# Как устроен проект

## Структура

```text
project.godot                    настройки движка, ввод и автозагрузки
scenes/
  main.tscn                     Node Main — постоянная оболочка
  world.tscn                    Node3D World — один раунд
  player.tscn                   CharacterBody3D — игрок
  monster.tscn                  CharacterBody3D — сущность
scripts/
  art/                          импорт моделей, материалы и атмосферные события
  core/
    game_manager.gd             общие ссылки, команды ввода, локальный игрок
    network_manager.gd          ENet, лобби, роли, загрузка, завершение, RPC ввода
    settings_manager.gd         локальные графика/звук/мышь и ConfigFile
    audio_manager.gd            небольшие звуковые заглушки
  player/player_controller.gd   камера, движение, фонарь, здоровье, ввод
  ai/monster_ai.gd              конечный автомат сущности
  world/
    station.gd                 геометрия, навигация, взаимодействия, снимки мира
    item_system.gd             предметы и инвентарь
    objective_system.gd        питание, кассета, передача, таймер, исход
    interactable.gd            модели и коллизии объектов
  ui/
    main.gd                    меню, лобби, HUD, настройки, пауза, исход
    backdrop.gd                рисованный фон меню
tests/                          тесты Godot и захват рендера
tools/run_smoke.py              запускает несколько Godot для проверки LAN
docs/                           инструкции и планы
assets/                         GLB-модели, PNG-фактуры и шейдер оформления
art-source/                     редактируемая библиотека Blender; Godot не импортирует
graphify-out/                   локальные результаты анализа; не коммитить
test-results/                   локальные логи и кадры; не коммитить
```

Четыре скрипта в `core/` уже зарегистрированы в **Project → Project Settings → Globals → Autoload**. Повторно добавлять их не требуется. После изменения пути сначала исправьте соответствующую запись в `project.godot`.

## Дерево во время игры

```text
Main
├─ Interface (CanvasLayer)
│  └─ Control
│     ├─ экран меню / лобби / настройки / исход
│     └─ HUD
└─ World (Node3D)
   ├─ Players (Node3D)
   │  ├─ 1 (CharacterBody3D, хост)
   │  │  ├─ CollisionShape3D
   │  │  ├─ MeshInstance3D
   │  │  ├─ Label3D
   │  │  ├─ Head (Node3D)
   │  │  │  ├─ Camera3D
   │  │  │  └─ SpotLight3D
   │  │  └─ StateSync (MultiplayerSynchronizer)
   │  └─ <peer_id клиента> (та же структура)
   ├─ PlayerSpawner (MultiplayerSpawner)
   ├─ ItemSystem (Node)
   ├─ ObjectiveSystem (Node)
   ├─ Monster (CharacterBody3D)
   │  └─ StateSync (MultiplayerSynchronizer)
   ├─ WorldEnvironment
   ├─ Atmosphere                декорации, виньетка, ложные силуэты и пыль
   ├─ помещения и предметы
   └─ источники света
```

В дереве редактора большая часть этих узлов не видна до запуска. Во время F5 выберите вкладку **Remote** в панели Scene — там показано настоящее дерево работающей игры. Размеры помещений и места предметов задаются в `station.gd::_build_station()`.

## Ввод и движение

`GameManager._ready()` создаёт InputMap: WASD, Shift, Ctrl, E, F, Q, G, R, V, Esc. Используются физические клавиши — русская раскладка не меняет управление.

`PlayerController` хранит `peer_id` как владельца ввода, но **multiplayer authority остаётся у хоста с ID 1**. Это разные понятия. Только локальный игрок делает свою камеру текущей. Мышь меняет локальные углы сразу. При Esc курсор освобождается и ввод движения прекращается, сама сеть не ставится на паузу.

Клиент примерно 30 раз в секунду отправляет направление, углы, бег, присед и удержание E. Он не отправляет координаты. Хост ограничивает длину направления до 1, проверяет конечность чисел, ограничивает наклон камеры, применяет фиксированную скорость, гравитацию и `move_and_slide()`. Если ввод не приходил 0.3 секунды, движение и взаимодействие прекращаются.

В этой версии присед уменьшает скорость и высоту камеры, но не меняет капсулу коллизии: пролезание в вентиляцию ещё не реализовано. При добавлении изменения коллизии нужно проверять свободное место над головой перед вставанием.

Результат движения записывается в `net_position`. `MultiplayerSynchronizer` отправляет его примерно 20 раз в секунду. Клиенты плавно приближают отображаемое тело к этой позиции. Для небольшого LAN-пинга этого достаточно для проверки механик. Следующий шаг для интернета — предсказание, номера команд и сверка с хостом.

## Пошагово: подключение и спавн

1. `host_room()` создаёт `ENetMultiplayerPeer`, вызывает `create_server(port, 3)`: три клиента плюс сам хост дают четыре участника.
2. `join_room()` проверяет IP, вызывает `create_client(ip, port)` и ждёт подтверждения подключения.
3. После `connected_to_server` клиент вызывает `register_player` у peer 1. Хост проверяет версию протокола, вместимость и состояние комнаты, добавляет позывной и свободную роль.
4. `_sync_lobby` отправляет всем подтверждённый список. Роли не могут повторяться; выбор занятой роли меняет двух участников местами. Вход в активный раунд отклоняется.
5. До двух участников доступны две объединённые роли. Начиная с трёх — четыре отдельных роли. При выходе из лобби с уменьшением состава роли нормализуются.
6. Только хост запускает раунд. `_prepare_round` передаёт номер раунда всем и заставляет каждый процесс создать `Main/World`.
7. Когда карта, спавнер и синхронизаторы готовы, клиент сообщает `client_world_ready`. Хост ждёт **всех**, затем начинает спавн. Таймаут загрузки — 20 секунд.
8. `MultiplayerSpawner.spawn()` создаёт персонажей по одинаковой функции на всех компьютерах. В данных передаются ID, позывной, роль, начальная позиция.
9. `spawn_function` возвращает персонажа, ещё не добавленного в дерево. Сам `MultiplayerSpawner` добавляет его в `Players`. Повторный `add_child()` здесь был бы ошибкой.

Минимальный смысл кода подключения (полная обработка ошибок уже есть в проекте):

```gdscript
var peer := ENetMultiplayerPeer.new()
var error := peer.create_server(27840, 3)
if error == OK:
    multiplayer.multiplayer_peer = peer

# В другом процессе:
var client := ENetMultiplayerPeer.new()
var connect_error := client.create_client("192.168.1.10", 27840)
if connect_error == OK:
    multiplayer.multiplayer_peer = client
```

Не вставляйте оба фрагмента последовательно в один работающий экземпляр: это пример для двух разных процессов.

## MultiplayerSpawner, MultiplayerSynchronizer и RPC

У спавнера `spawn_path = "../Players"`, потому что сам он лежит в `World/PlayerSpawner`. Имена `World`, `Players` и имя персонажа по ID должны совпадать на всех участниках. Произвольные автоматически полученные имена вроде `@CharacterBody3D@2` для сетевых объектов не подходят.

У `StateSync` корень по умолчанию `..`. Пути в `SceneReplicationConfig` имеют вид `.:net_position`, `.:health`. Это свойства корневого персонажа, а не свойства синхронизатора. Передаются векторы, числа, bool, строки и массив строк. Не передавайте через синхронизатор `Resource`, ссылку на ноду, RID или ID объекта из памяти одного процесса.

```gdscript
var config := SceneReplicationConfig.new()
var property := NodePath(".:net_position")
config.add_property(property)
config.property_set_replication_mode(
    property, SceneReplicationConfig.REPLICATION_MODE_ALWAYS
)
sync.replication_config = config
sync.replication_interval = 0.05
```

`@rpc("any_peer", "call_remote", "unreliable_ordered", 1)` разрешает клиентам передавать частый ввод на отдельном канале. Потеря старого пакета допустима — следующий заменит его. Хост определяет персонажа по `multiplayer.get_remote_sender_id()`, а не по присланному ID. Номер раунда отсекает задержавшийся ввод из прошлого раунда.

`@rpc("authority", "call_local", "reliable")` разрешает только хосту объявлять начало раунда, состояние лобби и другие подтверждённые события. `call_local` нужен, чтобы событие выполнилось и у хоста-игрока. Хост свой ввод применяет локальной функцией: не требуется отправлять RPC самому себе.

Критичные события — надёжные. Позиции и одноразовые звуковые эффекты могут теряться. Не передавайте текстуры и звук в пакетах: все копии игры уже имеют один и тот же ресурс или синтезатор, по сети достаточно названия эффекта и позиции.

Документация: [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html), [MultiplayerSpawner](https://docs.godotengine.org/en/stable/classes/class_multiplayerspawner.html), [MultiplayerSynchronizer](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html).

## Авторитет хоста: предметы и цели

Клиент не сообщает «я поднял предмет №5». Он удерживает E. Хост выпускает луч из рассчитанных им глаз персонажа, с дальностью 2.6 метра и учётом стен. Только найденный лучом объект допускается к взаимодействию. Для дверной кнопки луч возвращает саму дверь.

`ItemSystem.pickup()` проверяет доступность, вместимость и тяжёлую канистру для медика. Предмет сначала помечается занятым на хосте, затем меняется инвентарь и передаётся снимок мира. Поэтому два одновременных подбора не создают две копии. `taken` сохраняет объект как запись мира, а визуальную модель и коллизию скрывает. Выкладывание создаёт новый объект с уникальным ID. Серверные внутренние методы не являются RPC и не вызываются клиентами напрямую.

`ObjectiveSystem` последовательно принимает предохранитель и бензин, считает время ремонта, затем принимает кассету. Хост каждый кадр формирует списки тех, кто действительно удерживает E у устройств. В живой команде финал проходит только при разных ID у щита и передатчика. Если взаимодействие прервано, прогресс передачи убывает. Для единственного живого персонажа действует учебное упрощение.

Таймер, расход батареи, урон, оглушение и победа считаются на хосте. Для последнего живого персонажа действует учебное упрощение финала и переноски канистры, чтобы смерть напарника не блокировала сценарий. Визуальная вспышка и звук могут исполняться у всех. Нельзя рассчитывать победу отдельно на каждом клиенте: время и состояние могут отличаться.

## Отключение и повторный раунд

При отключении клиента хост выкладывает его инвентарь и удаляет персонажа. Спавнер передаёт удаление остальным. Существующий матч продолжается. Новый вход разрешён после возвращения в лобби; возвращения в прежнего персонажа пока нет.

Для выхода в лобби все прекращают ввод. Хост удаляет персонажей через спавнер, клиенты подтверждают пустой контейнер. Только после этого все удаляют карту. Это предотвращает сообщения к уже удалённым сетевым нодам. Ввод поступает в постоянный `NetworkManager`, поэтому старые пакеты не ищут исчезнувший `Players/<id>`.

Если соединение с хостом потеряно, клиент закрывает ENet, удаляет карту и показывает главное меню. Продолжить этот матч без хоста пока нельзя.

## Сущность по этапам

1. **DORMANT:** первые 30 секунд игроки осматриваются.
2. **PATROL:** сущность идёт между точками через сетку AStarGrid2D. Стены, крупная мебель и закрытые двери препятствуют маршруту.
3. **INVESTIGATE:** шум внутри радиуса заставляет идти к источнику. Бег слышно дальше ходьбы; V и генератор — ещё дальше.
4. **CHASE:** видимый живой игрок становится целью. Проверка видимости выполняется примерно каждые 0.18 секунды, маршрут пересчитывается каждые 0.5 секунды.
5. **SEARCH:** потеряв видимость, сущность доходит к последней известной точке и некоторое время ищет.
6. **Атака:** с дистанции около 1.45 м и при прямой видимости наносится 40 урона, с перерывом 2 секунды. Короткая неуязвимость исключает удар каждый физический кадр.
7. **RETREAT:** если направить работающий фонарь на сущность ближе 5.5 м, она ненадолго отступает. Это расходует батарею, а не уничтожает врага.
8. **Возврат:** после поиска снова патрулирует. Редкая смена позиции разрешена только вдали от игроков и вне их прямой видимости.

На хосте работает весь автомат, на клиентах — только отображение позиции и состояния. Звуки здесь синтетические; настоящих голосов, распознавания крика и микрофона нет. Слышимость пока задаётся радиусом, без затухания через стены. Для сложной многоэтажной карты AStarGrid2D следует заменить на NavigationRegion3D/NavigationAgent3D с подготовленной навигационной сеткой.

## Готовность к онлайн-режиму

Игровые системы уже не зависят от адреса подключения: транспорт и вход находятся в NetworkManager. Для интернета отдельно потребуются выбор стратегии соединения, NAT traversal или relay, ограничения частоты сообщений, аутентификация при необходимости, предсказание движения, тестирование потерь пакетов и задержек. ENet через LAN сам по себе этих задач не решает. На первом этапе ничего из этого не требует платного сервиса.
